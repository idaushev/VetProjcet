# UI/UX бэклог VetClinic

Дата аудита: 2026-09-02 · версия 2.90.0

Все цифры измерены на живом стенде, а не оценены на глаз. Основной viewport
для замеров — **768×1024** (iPad portrait): это рабочее устройство клиники.

## Что за приложение

Ванильный JS без фреймворка, 13 853 строки JS и 2 993 строки CSS. Разметка
собирается конкатенацией строк в `ui.js` (общие формы и компоненты) и
`pages.js` (страницы), плюс шесть модулей: чипирование, расписание, печать,
склад, протоколы, телеграм. Роутинг свой — `navigate(page)` переключает
`.page.active`, 14 страниц. Действия делегируются через `data-act`
(`actions.js`, реестр на 118 имён). Дизайн-токены есть: `--fs-*`, `--r-*`,
`--ctl-h`, `--touch: 52px`, цветовые роли. Тач уже частично учтён:
`@media (pointer: coarse)` меняет базовый кегль, у кнопок высота `--touch`.

То есть фундамент заложен. Проблемы — в непоследовательности его применения.

## UX-001 — Треть тач-целей меньше 44px

**Priority:** P0
**Area:** Tablet / Touch

**Problem.** На 768×1024 из 266 интерактивных элементов **83 (31%)** имеют
хотя бы одну сторону меньше 44px — нижней границы WCAG 2.5.5. Худшее:
иконочные кнопки в списках каталога и персонала — **36×36px**; кнопки на
дашборде и в приёмах — высотой 38px; вкладки настроек — 42px.

Токен `--touch: 52px` в проекте есть, но применён только к `.btn` без
модификаторов. `.btn-sm` и `.btn-icon` его не наследуют.

**Impact.** Промахи пальцем на основном рабочем устройстве. В списке
каталога кнопки «править» и «удалить» стоят рядом по 36px — промах по
соседней означает удаление позиции.

**Proposed solution.** В `@media (pointer: coarse)` поднять минимальный
размер всех интерактивных элементов до 44px, а у деструктивных соседей
развести центры не меньше чем на 8px. Размер задавать через `min-height`/
`min-width`, чтобы визуальный размер кнопки не менялся — растёт только
область попадания.

**Acceptance criteria.** На 768×1024 и 1024×768 доля целей меньше 44px = 0%.
Визуальный размер кнопок в десктопе не изменился.

**Affected components.** `.btn-sm`, `.btn-icon`, `.settings-tab`, `.sched-cell`.

**Risk.** Низкий: правится в медиазапросе для касания, десктоп не трогается.

## UX-002 — 62 подсказки доступны только по наведению

**Priority:** P0
**Area:** Accessibility / Tablet

**Problem.** В интерфейсе 69 атрибутов `title=`, из них **62 без
`aria-label`**. На планшете наведения нет вовсе — подсказка недостижима.
Пять иконочных кнопок не имеют ни подписи, ни `aria-label`: назначение
кнопки на планшете не узнать никак.

Механизм пояснений по нажатию (`UI.hint`) в проекте уже есть — он просто не
применён к `title`.

**Impact.** Прямо нарушает требование «не проектировать так, будто hover
существует всегда». Для иконок удаления и изменения статуса это ещё и риск
ошибочного действия.

**Proposed solution.** Каждому `title` добавить `aria-label` с тем же
текстом (одна правка, одно место — генераторы кнопок). Иконочным кнопкам без
имени — обязательный `aria-label`. `title` оставить: на десктопе он полезен.

**Acceptance criteria.** `title` без `aria-label` = 0. Иконок без доступного
имени = 0. Скринридер называет каждую кнопку.

**Affected components.** `.btn-icon` во всех списках, `rowMenu`, тулбары.

**Risk.** Низкий.

## UX-003 — Строки списка прыгают по высоте от длины имени

**Priority:** P0
**Area:** Layout stability

**Problem.** Строки списка владельцев имеют высоту **77px или 98px** в
зависимости от длины ФИО: длинное имя переносится на вторую строку. Список
животных при этом стабилен — 77px всегда, потому что там текст обрезается.
То есть два одинаковых по смыслу списка ведут себя по-разному.

Проверено на ФИО «Константинопольский-Задунайский Аполлинарий Вениаминович».

**Impact.** Ровно то, на что жалуется заказчик: элементы скачут в зависимости
от контента. Ритм списка ломается, глазу не за что зацепиться при
просматривании.

**Proposed solution.** Единое правило обрезки для всех строк списка:
заголовок и подстрочник в одну строку с многоточием, высота строки
фиксирована. Полное значение доступно в карточке.

**Acceptance criteria.** Во всех списках (владельцы, животные, приёмы,
вакцинации, каталог, персонал, чипы) высота строки одна и та же независимо
от контента.

**Affected components.** `.erow`, `.erow-title`, `.erow-sub`.

**Risk.** Низкий. Внимание: не обрезать там, где значение обязано быть видно
целиком (номер чипа).

## UX-004 — Двенадцать произвольных брейкпоинтов

**Priority:** P1
**Area:** Responsive

**Problem.** В CSS 12 разных границ: 420, 520, 599, 640, 720, 768, 899,
900–1099, 1100, 1200, 1400, 1500, 1800. Системы нет — каждая появлялась под
конкретную поломку.

**Impact.** Поведение между 899 и 900 или между 1099 и 1100 непредсказуемо;
любая правка макета требует проверки на десятке ширин.

**Proposed solution.** Свести к четырём заявленным опорным ширинам:
768 / 1024 / 1280 / 1440, оставив `pointer: coarse` отдельной осью (это про
палец, а не про ширину). Существующие правила перевесить на ближайшую
границу.

**Acceptance criteria.** В CSS не больше 5 ширинных брейкпоинтов. Проверены
1440×900, 1280×800, 1024×768, 834×1194, 768×1024, 390×844.

**Risk.** Средний: перенос правил между границами может сдвинуть частные
случаи. Делать с проверкой на всех шести viewport.

## UX-005 — Двадцать восемь значений отступов вместо шкалы

**Priority:** P1
**Area:** Design system

**Problem.** В CSS встречаются отступы 3, 5, 7, 9, 11, 13, 22, 26px и ещё
двадцать значений. Шкалы нет.

**Impact.** Вертикальный ритм плавает, одинаковые по смыслу блоки отбиты
по-разному. Каждое новое место приходится подбирать на глаз.

**Proposed solution.** Ввести шкалу 4/8/12/16/20/24/32/40 токенами
`--sp-1…--sp-8` и перевести на неё значения, не попадающие в шкалу
(округляя к ближайшему шагу).

**Acceptance criteria.** Значений вне шкалы не осталось; визуальных
регрессий на шести viewport нет.

**Risk.** Средний по объёму, низкий по сути.

## UX-006 — Один и тот же тип действия выглядит по-разному

**Priority:** P1
**Area:** Buttons

**Problem.** Порядок классов кнопки не унифицирован: `btn btn-ghost btn-sm`
(33 места) и `btn btn-sm btn-ghost` (14), `btn btn-primary btn-sm` (4) и
`btn btn-sm btn-primary` (4). Визуально это одно и то же, но правка стилей
по одному из написаний промахивается мимо второго. Плюс единичные гибриды:
`btn-icon btn-print`, `btn-icon btn-open`, `btn-add-vitem`.

**Impact.** Системная правка кнопки чинит не все места — ровно та ловушка,
о которой говорит бриф («если Button выглядит неправильно на 15 страницах —
исправь Button»).

**Proposed solution.** Один порядок: `btn btn-<вид> btn-<размер>`. Одиночные
гибриды свести к модификаторам.

**Acceptance criteria.** Ни одного написания в обратном порядке.

**Risk.** Низкий.

## UX-007 — Терминология расходится

**Priority:** P1
**Area:** Content

**Problem.** Одну сущность называют по-разному: «Приём» (44) против «Визит»
(4 — в отчёте и печатной форме), «Владелец» (29) против «Клиент» (5 — в
отчёте не пришедших, в тосте и на листе Excel), «Удалить» (36) против
«Убрать» (4).

**Impact.** Сотрудник не уверен, что «Визиты» в отчёте — это те же приёмы.

**Proposed solution.** Закрепить словарь: приём, владелец, животное,
удалить. Исключение оставить одно: лист Excel «Клиенты» — так его ждут
бухгалтеры (или переименовать вместе с шаблоном импорта).

**Acceptance criteria.** В интерфейсе нет «Визит» и «Клиент» как синонимов.

**Risk.** Низкий.

## UX-008 — Абстрактные подписи действий

**Priority:** P1
**Area:** Buttons / Content

**Problem.** Кнопки «Сформировать» (4 места), «Обновить» (3), «Установить»,
«Все» — из подписи не следует, что произойдёт.

**Impact.** Приходится вспоминать или пробовать.

**Proposed solution.** Конкретный глагол с объектом: «Сформировать отчёт»,
«Обновить список», «Установить токен». Фильтры («Все», «Сегодня», «Неделя»)
не трогать — там объект задан контекстом группы.

**Acceptance criteria.** Каждая кнопка действия называет объект.

**Risk.** Низкий.

## UX-009 — Форма приёма — 1,6 экрана прокрутки

**Priority:** P1
**Area:** Forms

**Problem.** На 768×1024 форма нового приёма — 1300px при видимых 832px:
15 полей и 5 сворачиваемых секций. Секции есть, но открыты все сразу.

**Impact.** Основной ежедневный сценарий требует прокрутки и поиска нужного
блока.

**Proposed solution.** Открывать только текущий шаг, остальные свернуть;
свёрнутая секция показывает сводку заполненного. Порядок групп — по ходу
приёма: владелец и животное, данные приёма, услуги, оплата.

**Acceptance criteria.** При открытии формы видна первая секция целиком и
заголовки остальных; переход между секциями без прокрутки к началу.

**Risk.** Средний: трогает основной сценарий, нужна проверка на планшете.

## UX-010 — Дашборд не отвечает на вопрос «что делать сейчас»

**Priority:** P2
**Area:** Dashboard / Information hierarchy

**Problem.** 8 карточек, 17 интерактивных элементов, 5 заголовков,
1,4 экрана прокрутки. Счётчики и списки соседствуют, визуальный вес почти
одинаковый.

**Impact.** Первым в глаза попадает не то, что требует действия.

**Proposed solution.** Порядок по брифу: что требует внимания → что
происходит сегодня → быстрый поиск пациента → остальное ниже и легче.

**Acceptance criteria.** Блок «Требуют внимания» — первый экран без
прокрутки на 768×1024.

**Risk.** Средний: перестановка привычного экрана.

## UX-011 — 86 мест переключают видимость через style.display

**Priority:** P2
**Area:** Layout stability

**Problem.** Появление и исчезновение блоков сдвигает соседей. Замеры на
форме владельца показали 0px сдвига (сетка держит), но правило не
гарантировано — оно держится случайно, а не по конструкции.

**Proposed solution.** Для блоков, появляющихся предсказуемо (подсказка
валидации, предупреждение), резервировать высоту; для остальных — проверить
поштучно.

**Risk.** Низкий.

## UX-012 — Иконка как единственный носитель смысла

**Priority:** P2
**Area:** Icons

**Problem.** В списках действия «править» и «удалить» переданы только
иконкой. На узких экранах подпись не появляется.

**Proposed solution.** Деструктивное действие убрать из строки в меню «⋯»
(механизм уже есть), оставив в строке одно частое действие с подписью.

**Risk.** Средний: меняет привычное расположение.
